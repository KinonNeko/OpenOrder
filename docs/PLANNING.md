# OpenDiscord 项目规划

> 开源 Discord 替代品 —— 需求整理、技术路线与价值评估
> 2026-08-21 初版

---

## 一、项目定位

一句话定位:**可自托管的、Discord 级体验的开源社区通讯平台**,以实时消息与语音为核心,以插件生态和充分开放的 API 为长期护城河。

三个关键词决定了所有后续决策:

1. **Discord 级体验** —— 对标的是 Discord 的交互密度和流畅度,而不是 IRC/Matrix 式的"能用"。这是与现有开源竞品最大的差异点。
2. **自托管优先** —— 单机 Docker Compose 一键起服是一等公民,官方托管服务是其上的商业层,而非反过来。
3. **平台而非应用** —— API 覆盖全部功能面,Bot/插件是生态核心,不是附加品。

## 二、需求整理

### 2.1 功能需求(按优先级)

#### P0 — 实时消息(第一个可用版本的核心)

| 模块 | 需求 |
|---|---|
| 组织结构 | 服务器(Guild)→ 分类 → 频道;私信(DM)与群组 DM;线程(Thread) |
| 消息 | Markdown 富文本、附件/图片/视频、自定义表情、回应(Reaction)、回复引用、编辑/删除、@提及、置顶 |
| 实时性 | WebSocket 网关推送;输入中指示;在线状态(Presence);未读计数与已读位置同步 |
| 历史与检索 | 无限历史回溯、跳转、全文搜索 |
| 权限 | 角色系统 + 频道级权限覆盖(Discord 的 allow/deny 位掩码模型是成熟答案,直接借鉴) |
| 审核 | 踢出/封禁/禁言(Timeout)、慢速模式、审计日志、内容举报 |
| 通知 | Web Push;移动推送(FCM/APNs + UnifiedPush);按频道/服务器细粒度静音 |

#### P0 — 语音会议

| 模块 | 需求 |
|---|---|
| 语音频道 | Discord 式常驻语音房间:进入即通话,状态对全服可见 |
| 音频质量 | Opus 编码、噪声抑制(RNNoise 级)、回声消除、自动增益;服务端混音不做,走 SFU 转发 |
| 视频/共享 | 摄像头视频、屏幕共享(含系统声音,分平台尽力而为) |
| 控制 | 服务器静音/闭麦、拖拽移动成员、频道人数上限 |
| 延期(P2) | 服务端录制、Stage 大型演讲频道、直播(Go Live)、空间音频 |

#### P1 — 社区平台

- 公开社区目录与发现页;邀请链接(可过期/限次)
- 新成员 Onboarding:规则确认、自助领取身份组、引导问题
- 频道类型扩展:论坛频道(帖子制)、公告频道(可被其他服务器订阅)
- 活动日历(Event):报名、提醒、关联语音频道
- 服务器模板、Banner/主题定制

#### P0(架构约束)/ P1(功能交付)— 插件与 API

- **REST API 全量覆盖**:客户端能做的一切,API 都能做(客户端本身就是 API 的消费者,dogfooding)
- **Gateway 事件流**:Bot 以 WebSocket 订阅事件,与人类客户端同构
- **OAuth2**:第三方应用授权、Bot 安装流程
- **Webhook**:入站(向频道发消息)与出站(事件回调)
- **服务端插件**:进程内扩展点(消息过滤、自定义命令、鉴权钩子),沙箱方案见技术路线
- **客户端插件/主题**:官方支持而非社区逆向(Discord 封杀 BetterDiscord 的痛点即是机会)
- **斜杠命令**:Bot 注册命令,客户端自动渲染 UI(参数补全、弹窗表单)

#### P0 — 部署形态

- 单机:`docker compose up` 十分钟内可用,含 TLS 引导(Caddy/Traefik)
- 集群:Helm Chart,网关/API/语音可独立横向扩展
- 依赖收敛:PostgreSQL + Redis + S3 兼容存储(MinIO),不引入更多必选组件
- 账号:本地注册 + OIDC/LDAP 单点登录(自建场景刚需)
- 官方托管:与自建版同一代码库,配置差异而非代码分叉

### 2.2 非功能需求

- **性能基线**:单节点(4C8G)支撑 5,000 并发在线、50 人语音房间不劣化;协议设计为水平扩展留余地
- **端覆盖**:Web 优先 → 桌面(Web 套壳)→ 移动原生体验;三端功能对齐是长期承诺
- **数据主权**:完整导入/导出工具;提供 Discord 数据迁移器(服务器结构、历史消息尽力迁移)
- **隐私差异化**:DM 端到端加密(MLS 协议)作为 P2 —— Discord 至今没有 E2EE 文字消息,这是真实差异点
- **i18n** 与无障碍(键盘导航、读屏)从第一天纳入组件规范

### 2.3 明确不做(v1 非目标)

- Matrix 式联邦(见架构决策 A)
- Nitro 式增值功能、经济系统
- 音视频自研 SFU(直接用成熟开源,见决策 C)
- 消息级微服务拆分(先单体)

## 三、技术路线

### 3.1 四个关键架构决策

**A. 联邦 vs 中心化多实例 → 选中心化多实例**

Matrix 证明了联邦的代价:状态解析复杂度高、性能差、UX 受协议拖累。Discord 模型(一个实例内多服务器)简单可靠。自托管本身已解决数据主权问题,联邦解决的"跨实例社交图谱"留作远期(可通过实例间账号漫游/邀请协议渐进实现),不进入 v1 协议设计。

**B. 是否兼容 Discord API → 自有 API 为主,兼容层为插件**

兼容 Discord API(Spacebar 路线)可以白嫖庞大的 Bot 生态,但:Discord API 有大量历史包袱;追着别人的 API 演进永远被动;Spacebar 多年未达可用状态即是前车之鉴。
决策:**API 自主设计、概念对齐**(guild/channel/role 语义保持直觉一致),另提供一个 **Discord 兼容垫片插件**(翻译 REST 路径与 Gateway 事件),让 discord.js / discord.py 写的 Bot 低成本迁移。垫片可以不完美,自有 API 必须干净。

**C. 语音自研 vs 集成 → 集成 LiveKit**

WebRTC SFU 是深水区(拥塞控制、Simulcast、平台兼容)。**LiveKit**(Apache-2.0,Go/Pion)提供:成熟 SFU、全平台 SDK、屏幕共享、服务端录制(Egress)、噪声抑制,且支持自托管。Element Call 也已转向基于 LiveKit 的架构,验证了该路线。
集成方式:我们的后端签发 LiveKit JWT,语音频道映射为 LiveKit Room,权限由主系统统一裁决。备选:mediasoup(更底层,需自建信令与 SDK 层,不推荐首选)。

**D. 后端语言 → Go(务实首选)或 Rust**

Discord 自己用 Elixir 做网关是最佳技术匹配,但 Elixir 贡献者池太小,与"社区驱动的开源项目"目标冲突。
- **Go**:并发模型足够、生态成熟、贡献门槛低、与 LiveKit 同栈 —— 推荐
- Rust:性能与正确性更佳,Revolt 已验证,但迭代速度和贡献门槛吃亏
架构形态:**模块化单体**(auth / messaging / gateway / voice-control / plugin-host 为清晰模块边界),网关(WebSocket 扇出)是第一个值得独立部署的组件,其余不过早拆分。

### 3.2 技术选型总表

| 层 | 选型 | 备注 |
|---|---|---|
| 后端 | Go 模块化单体 | 网关可独立横向扩展 |
| 实时协议 | WebSocket + JSON(预留 MessagePack 压缩协商) | 事件语义参考 Discord Gateway 但自主定义 |
| 消息存储 | PostgreSQL(按 channel_id + 时间分区) | Discord 的 ScyllaDB 路线是十亿级消息后的事,PG 能撑很久 |
| 缓存/PubSub | Redis(Presence、网关扇出、限流) | |
| 对象存储 | S3 兼容(自带 MinIO) | 图片缩略图/转码走异步 worker |
| 搜索 | PG 全文检索起步 → Meilisearch 可选增强 | 中文分词需注意(pg_jieba / Meilisearch 自带) |
| 语音视频 | LiveKit 自托管 | 主系统签发 Token,统一权限 |
| Web 客户端 | React + TypeScript;虚拟列表是消息流核心技术点 | UI 组件库自建设计系统 |
| 桌面 | Tauri(体积与内存远优于 Electron) | 需处理屏幕共享的平台差异 |
| 移动 | React Native(与 Web 共享逻辑层) | 语音用 LiveKit RN SDK |
| 推送 | FCM/APNs + UnifiedPush(去 Google 化选项) | 自托管场景的推送代理需专门设计 |
| 服务端插件 | 进程内 Go 插件谨慎;首选 WASM(wazero)沙箱 + 出站 Webhook | 安全边界清晰 |
| 部署 | Docker Compose(单机)+ Helm(集群) | |

### 3.3 里程碑

| 阶段 | 周期 | 交付物 |
|---|---|---|
| M0 协议与骨架 | 第 1–2 月 | API/Gateway 协议规范(先写文档)、单体骨架、认证、频道与消息 CRUD、最小 Web 端(能聊天) |
| M1 消息完整体 | 第 3–5 月 | 权限/角色、线程、表情回应、搜索、未读同步、通知、Docker 一键部署 → **公开首个 Alpha** |
| M2 语音 | 第 5–8 月 | LiveKit 集成、语音频道、屏幕共享、桌面端(Tauri)→ **可日常使用的 Beta** |
| M3 平台化 | 第 8–12 月 | Bot API + OAuth2 + Webhook + 斜杠命令、WASM 插件宿主、Discord 兼容垫片(实验)、社区发现、移动端 |
| M4 生态与商业 | 12 月+ | 官方托管服务、E2EE DM(MLS)、大规模优化、实例间漫游探索 |

> 人力假设:2–4 名全职工程师。若是单人业余项目,砍掉移动端与兼容垫片,M1+M2 约需 12 个月 —— 范围裁剪是生死问题。

## 四、竞品格局

| 项目 | 定位 | 强项 | 短板(即我们的机会) |
|---|---|---|---|
| Revolt | 最接近的开源 Discord 复刻(Rust,AGPL) | UX 相似度高、社区活跃 | 语音长期薄弱、API/插件生态小、自托管体验一般 |
| Spacebar(前 Fosscord) | Discord API 兼容实现 | 理论上直接用 Discord 客户端/Bot | 多年未达生产可用,验证了"纯兼容"路线的困难 |
| Matrix / Element | 联邦协议 + E2EE | 政府/机构采用(德、法等)、协议开放 | UX 与 Discord 差距大、联邦拖累性能、语音(Element Call)仍在追赶 |
| Rocket.Chat / Mattermost | 团队协作(Slack 替代) | 企业功能、合规 | 面向工作而非社区,无 Discord 式语音房与社区结构 |
| Zulip | 话题流模型 | 异步讨论体验独特 | 同上,非社区平台 |
| TeamSpeak / Mumble | 纯语音 | 低延迟口碑 | 无现代消息/社区功能 |

**结构性空隙:没有任何一家同时做到"Discord 级 UX + 能打的语音 + 认真的插件生态 + 顺滑自托管"。** Revolt 最接近但语音与平台化是其多年短板;这正是本项目把语音(P0 + LiveKit)和 API(架构约束级)前置的原因。

## 五、价值评估

### 5.1 需求真实性 — 高

- **平台风险**:Discord 涨价、广告化倾向、封号不可申诉、政策单方面变更,社区无迁移能力
- **数据主权**:Discord 消息不加密、数据不可导出(社区历史是人质);机构/教育/开源组织对自托管有真实合规需求
- **可用性**:Discord 已在俄罗斯、土耳其等地被封锁,部分地区长期不可达 —— 自建服务器是刚需而非偏好
- **市场信号**:Revolt 数万 GitHub star;Matrix 获多国政府采用;Discord 自身 MAU 数亿 —— 品类被充分验证

### 5.2 核心风险 — 诚实评估

1. **网络效应是最硬的墙**。"你的朋友都在 Discord"无法用功能解决。对策:不打正面替代战,主攻"整个社区一起迁移"的场景(公会、开源项目、课程、隐私敏感社群)—— 决策单元是社区管理员,不是个人用户。
2. **工程量真实且巨大**。三端客户端 + 实时基础设施 + 语音,是数人年级别的投入;Revolt/Spacebar 的多年长跑就是标尺。对策:范围纪律(见非目标清单)+ 最大化借力(LiveKit、成熟组件)。
3. **开源变现难**。个人用户付费意愿低。可行路径:open-core(SSO/审计等企业特性)+ 官方托管 + 大社区技术支持;Mattermost/Element 验证过此模型,但都不轻松。
4. **内容审核责任**。提供公开社区发现即承担平台责任;托管服务需要信任与安全投入。自托管形态天然分散了这一风险。

### 5.3 结论

- **作为开源项目:值得做。** 生态位真实存在(见竞品空隙),即使不"赢",一个语音能打、API 完整的自托管社区平台也有清晰的用户群;对开发者本人,这是覆盖实时系统、WebRTC、分布式、客户端工程的高价值项目。
- **作为商业项目:高风险,但有窄门。** 不以取代 Discord 为叙事,以"社区基础设施的 self-hosted 选项"切入垂直场景(教育、开源基金会、受审查地区、隐私敏感社群),托管 + open-core 变现。
- **最大的败因预测是范围失控**,不是竞争。严格执行"明确不做"清单,把 Alpha 提前到 M1,用真实社区反馈驱动后续优先级。

### 5.4 立即下一步

1. 写协议规范初稿(API + Gateway 事件),先于代码
2. 搭 Go 单体骨架 + PG/Redis/MinIO 的 compose 文件
3. 打通"两个浏览器实时聊天"的最小闭环
4. LiveKit 本地起服,验证 Token 签发与房间映射的集成假设
